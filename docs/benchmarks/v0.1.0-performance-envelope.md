### 1.2 Measurement Rules & Telemetry Definitions

* **Synchronous End-to-End Exporter Pipeline (`sending_queue` disabled)**: `runSingleSignal` sets `expCfg.QueueSettings = configoptional.None` so `ConsumeTraces`, `ConsumeLogs`, and `ConsumeMetrics` measure synchronous end-to-end execution through Step-0 redaction (`internal/redact`), OTLP-to-row transformation (`internal/transform`), dynamic protobuf marshaling (`internal/protoenc`), stream-pool routing, and Storage Write API `AppendRows` acknowledgement.
* **Per-Batch Call Context vs. Measurement Timer**: Workers check `runCtx` (`context.WithTimeout(ctx, cfg.Duration)`) before dispatching each batch, while each `Consume*` call receives `callCtx, cancelCall := context.WithTimeout(ctx, expCfg.TimeoutSettings.Timeout)` — a per-batch child of the caller `ctx` decoupled from `runCtx` so in-flight batches at the end of the measurement window drain cleanly unless `ctx` is canceled or the per-batch call timeout expires.
* **`Bytes/Row`, `AttemptedBytesPerAckedRow`, and `Encoded-Row MiB/s` (`wire_mb_per_sec`)**:
  * `Encoded-Row MiB/s` (`wire_mb_per_sec` in JSON) = `(otelcol_exporter_bigquery_append_bytes / 1,048,576) / elapsed_seconds` (total serialized `ProtoRows` row payload bytes passed to `AppendRows` across all attempts per second, before outer `AppendRowsRequest` protobuf/gRPC framing or transport compression).
  * `AttemptedBytesPerAckedRow` = `otelcol_exporter_bigquery_append_bytes / otelcol_exporter_bigquery_acknowledged_rows` (total serialized `ProtoRows` row payload bytes attempted across all `AppendRows` calls, including retries, per acknowledged row).
  * `Bytes/Row` = single-append serialized `ProtoRows` row payload bytes per acknowledged row (measured from acknowledged `ProtoRows` chunks in `bqfake` or single-attempt encoded batches before retries, excluding pre-append local offload failures, so whole-batch or split-chunk retries do not distort the reported row size).
* **Whole-Process CPU & Memory Telemetry**: `readProcessCPUAndRSS()` reads Linux `syscall.Getrusage(syscall.RUSAGE_SELF)` (`Utime + Stime` whole-process CPU seconds across the exporter pipeline, worker goroutines, and in-process `bqfake` server when `mode=bqfake`) and `Maxrss`, alongside `runtime.ReadMemStats` (`HeapAlloc` snapshot, `TotalAlloc` delta, `Mallocs` delta, and `NumGC` delta).

**Key Findings (Suite A)**:

1. Increasing `write.stream_pool_size` from `1` to `2`–`4` eliminates single-stream contention, boosting throughput by **`+48.5%` to `+56.1%` on `traces`** (`18,790.8 -> 27,896.1..29,333.9 rows/s`), **`+47.0%` to `+48.3%` on `metrics`** (`15,876.4 -> 23,342.2..23,544.2 rows/s`), and **`+19.8%` to `+28.0%` on `logs`** (`22,649.6 -> 27,133.1..28,983.0 rows/s`), while reducing `p50` append latency by **`32.7%`–`36.4%` on `traces`** (`103.80 -> 66.01..69.89 ms`), **`29.2%`–`30.1%` on `metrics`** (`119.76 -> 83.76..84.79 ms`), and **`16.5%`–`20.9%` on `logs`** (`86.10 -> 68.10..71.94 ms`).
2. **Engineering Hypothesis & Sizing Guidance**: Beyond `stream_pool_size = 4` (with `workers = 4` and `connection_pool_size = 4` on the `24`-vCPU benchmark host), throughput plateaus while `CPU Cores / 10k rows/s` rises from `1.89`–`2.59` to `2.16`–`3.27`. We attribute this plateau to per-row CPU serialization overhead (`google.golang.org/protobuf/types/dynamicpb` + JSON attribute marshaling) and recommend `stream_pool_size = 4` as the default starting point for `1`–`4` vCPU Collector deployments (noting that these measurements were collected on an unconstrained `24`-vCPU host rather than CPU-capped `1`–`4` vCPU containers).

## 6. Capacity & Tuning Recommendations (Illustrative Exporter & Collector Sizing)

> **Scope & Estimation Note**: The CPU and memory figures in Sections 2–5 measure `bigqueryexporter` on a `24`-vCPU host with `sending_queue` disabled so every batch is acknowledged synchronously. The **30%–50% CPU and memory headroom** and the replica allocations in the table below are **illustrative capacity-planning estimates** (extrapolated from the measured `CPU Cores / 10k rows/s` figures rather than separate full-Collector benchmarks on `1`–`4` vCPU instances) to account for OTLP gRPC/HTTP receivers, `memory_limiter`, `batch` processor queues, and `sending_queue` buffering when deploying inside a full OpenTelemetry Collector binary (`otelcol-contrib` or custom distribution).

| Target Sustained Rate (Combined Rows/s) | Recommended `write.stream_pool_size` | Recommended `write.connection_pool_size` | Estimated Exporter CPU (Unredacted / Redacted) | Illustrative Full Collector Replica Allocation (with Receiver + Batch + Queue Headroom) |
|---:|---:|---:|---|---|
| **$\le 2,500\text{ rows/s}$** | `2` | `2` | `0.5` / `0.8 vCPU` | `2` HA replicas $\times$ (`1 vCPU`, `2 GiB` RAM) |
| **$2,500\text{–}10,000\text{ rows/s}$** | `4` | `4` | `1.5` / `3.2 vCPU` | `2`–`3` HA replicas $\times$ (`2 vCPU`, `4 GiB` RAM) |
| **$10,000\text{–}50,000\text{ rows/s}$** | `8` | `4`–`8` | `6.0` / `15.5 vCPU` (across fleet) | `4`–`8` HA replicas $\times$ (`4 vCPU`, `8 GiB` RAM) |
