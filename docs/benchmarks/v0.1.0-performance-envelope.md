### Key Findings from Live BigQuery Measurements

1. **Stream Pool Sweet Spot (`write.stream_pool_size: 4`)**:
   - On live BigQuery newly auto-created tables, increasing `write.stream_pool_size` from `1` to `4` increases `otel_spans` throughput by **`+67.5%`** (from `13,104.4` spans/s / `36.75 MB/s` to **`21,943.6` spans/s / `61.53 MB/s`**) while cutting `p50` append latency from `160.46 ms` to **`118.54 ms`** and `p99` from `1,125.89 ms` to **`848.32 ms`**.
   - On freshly created tables (first ~10 seconds after `CREATE TABLE`), opening `8` simultaneous `_default` streams triggers initial BigQuery tablet Warm-Up tail spikes (`p95 ~ 1.47s`), whereas `write.stream_pool_size: 4` (with `connection_pool_size: 4`) saturates `61.5 MB/s` cleanly.
2. **Exporter Resource Efficiency**:
   - Across all live BigQuery runs, the exporter consumes **`1.30–1.67` vCPU cores per `10,000` rows/sec**, **`21.4–55.3 MB` of Go heap (`HeapAlloc`)**, and a steady **`123.0 MB` Peak RSS**.
3. **Production Sizing Rule of Thumb**:
   - **Up to `12,000` spans/s (`~35 MB/s` wire)**: `write.stream_pool_size: 1` (default) with `enable_multiplexing: true`, `2` vCPU, `512 MiB` container memory limit.
   - **`12,000` to `25,000` spans/s (`35–65 MB/s` wire)**: `write.stream_pool_size: 4`, `write.connection_pool_size: 4`, `write.backpressure.enabled: true`, `4` vCPU, `1 GiB` container memory limit.
   - **Above `25,000` spans/s (`>65 MB/s` wire)**: Scale horizontally across `2+` Collector replicas with `write.stream_pool_size: 4` per replica (or `stream_pool_size: 8` once destination table partitions are warm).
