* **Unified 4-Step Execution Tree Identity Across Signals**: Every record at sequence index `seq` maps to `treeID := seq / 4`, `stepInTree := seq % 4`, and `fwIdx := int(treeID % 7)`:
  1. `stepInTree == 0`: Root agent invocation span (`invoke_agent`, or `openinference.span.kind = "AGENT"` for CrewAI) carrying `gen_ai.input.messages` (`input.value` for CrewAI) of exact byte length `-payload-bytes`.
  2. `stepInTree == 1`: Child LLM completion span (`chat`, or `openinference.span.kind = "LLM"` for CrewAI) carrying `gen_ai.output.messages` (`output.value` for CrewAI) of exact byte length `-payload-bytes`.
  3. `stepInTree == 2`: Child tool execution span (`execute_tool`, or `openinference.span.kind = "TOOL"` for CrewAI) carrying `gen_ai.tool.call.result` (`output.value` for CrewAI) of exact byte length `-payload-bytes`.
  4. `stepInTree == 3`: Child MCP client span (`mcp.method.name` rotating across `tools/call` with `gen_ai.tool.name` + `gen_ai.tool.call.id`, `resources/read` with `mcp.resource.uri`, and `prompts/get` with `gen_ai.prompt.name`) carrying `mcp.payload.content` of exact byte length `-payload-bytes`.
* **Cross-Signal Join Conformance**: `LogsBatch` and `MetricsBatch` group records by the same `fwIdx` (`fw.ServiceName`, `fw.ScopeName`, `fw.ScopeVer`) and attach `traceIDFromTree(treeID)` and `spanIDFromPair(treeID, stepInTree)`. `MetricsBatch` alternates between `gen_ai.client.token.usage` (`unit: "{token}"`, `"input"` and `"output"` `gen_ai.token.type`) and `gen_ai.client.operation.duration` (`unit: "s"`) histogram data points with trace-correlated exemplars so `v_gen_ai_metric_exemplars` joins 100% of exemplars to their span on `(trace_id, span_id, service_name)`.

### 1.2 Measurement Rules & Telemetry Definitions

* **Synchronous End-to-End Exporter Pipeline (`sending_queue` disabled)**: `runSingleSignal` sets `expCfg.QueueSettings = configoptional.None` so `ConsumeTraces`, `ConsumeLogs`, and `ConsumeMetrics` measure synchronous end-to-end execution through Step-0 redaction (`internal/redact`), OTLP-to-row transformation (`internal/transform`), dynamic protobuf marshaling (`internal/protoenc`), stream-pool routing, and Storage Write API `AppendRows` acknowledgement.
* **Per-Batch Call Context vs. Measurement Timer**: Workers check `runCtx` (`context.WithTimeout(ctx, cfg.Duration)`) before dispatching each batch, while each `Consume*` call receives `callCtx, cancelCall := context.WithTimeout(ctx, expCfg.TimeoutSettings.Timeout)` — a per-batch child of the caller `ctx` decoupled from `runCtx` so in-flight batches at the end of the measurement window drain cleanly unless `ctx` is canceled or the per-batch call timeout expires.
* **`Bytes/Row`, `AttemptedBytesPerAckedRow`, and `Wire MiB/s`**:
  * `Wire MiB/s` = `(otelcol_exporter_bigquery_append_bytes / 1,048,576) / elapsed_seconds` (total serialized `ProtoRows` bytes transmitted across all `AppendRows` attempts per second).
  * `AttemptedBytesPerAckedRow` = `otelcol_exporter_bigquery_append_bytes / otelcol_exporter_bigquery_acknowledged_rows` (total wire bytes sent across all attempts, including retries, per acknowledged row).
  * `Bytes/Row` = single-append serialized `ProtoRows` wire bytes per acknowledged row (normalized by `batches_succeeded / (batches_succeeded + retries + batches_failed)` so retry storms do not artificially inflate the reported row size).
* **Whole-Process CPU & Memory Telemetry**: `readProcessCPUAndRSS()` reads Linux `syscall.Getrusage(syscall.RUSAGE_SELF)` (`Utime + Stime` whole-process CPU seconds across the exporter pipeline, worker goroutines, and in-process `bqfake` server when `mode=bqfake`) and `Maxrss`, alongside `runtime.ReadMemStats` (`HeapAlloc` snapshot, `TotalAlloc` delta, `Mallocs` delta, and `NumGC` delta).

**Key Findings (Suite A)**:

1. Increasing `write.stream_pool_size` from `1` to `2`–`4` eliminates single-stream mutex contention and boosts throughput by **`+48%` to `+56%`** across all three signals (`18,790.8 -> 29,333.9 rows/s` on traces; `15,876.4 -> 23,544.2 rows/s` on metrics) while cutting `p50` append latency by **`32%`–`36%`**.
2. Beyond `stream_pool_size = 4` (with `workers = 4` and `connection_pool_size = 4`), CPU serialization (`google.golang.org/protobuf/types/dynamicpb` + JSON marshaling) becomes the bottleneck; `stream_pool_size = 4` is the optimal default for 1–4 vCPU Collector instances.

## 6. Capacity & Tuning Recommendations (Exporter-Component Level)

> **Scope Note**: The CPU and memory figures in Sections 2–5 measure `bigqueryexporter` with `sending_queue` disabled so every batch is acknowledged synchronously. When deploying inside a full OpenTelemetry Collector binary (`otelcol-contrib` or custom distribution), add **30%–50% CPU and memory headroom** for OTLP gRPC/HTTP receivers, `memory_limiter`, `batch` processor queues, and `sending_queue` buffering.

| Target Sustained Rate (Combined Rows/s) | Recommended `write.stream_pool_size` | Recommended `write.connection_pool_size` | Exporter CPU Allocation (Unredacted / Redacted) | Full Collector Replica Allocation (with Receiver + Batch + Queue Headroom) |
|---:|---:|---:|---|---|
| **$\le 2,500\text{ rows/s}$** | `2` | `2` | `0.5` / `0.8 vCPU` | `2` HA replicas $\times$ (`1 vCPU`, `2 GiB` RAM) |
| **$2,500\text{–}10,000\text{ rows/s}$** | `4` | `4` | `1.5` / `3.2 vCPU` | `2`–`3` HA replicas $\times$ (`2 vCPU`, `4 GiB` RAM) |
| **$10,000\text{–}50,000\text{ rows/s}$** | `8` | `4`–`8` | `6.0` / `15.5 vCPU` (across fleet) | `4`–`8` HA replicas $\times$ (`4 vCPU`, `8 GiB` RAM) |
