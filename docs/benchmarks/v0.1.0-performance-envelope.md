## 2. Workload Profile & Measurement Methodology

All measurements use the deterministic workload generator in [`internal/testbench/generator.go`](../../internal/testbench/generator.go) and runner in [`internal/testbench/runner.go`](../../internal/testbench/runner.go):

- **7 GenAI Agent Frameworks**: `google_adk` (`gemini-2.5-pro`), `langgraph` (`gpt-4o-2026-05`), `openai_agents` (`o3-mini`), `anthropic_agent_sdk` (`claude-sonnet-4-20250514`), `crewai` (`gemini-2.5-flash`), `aws_bedrock` (`anthropic.claude-3-7-sonnet-20250219-v1:0`), and `microsoft_agent_framework` (`gpt-4.1`).
- **4-Span Agent Execution Trees**:
  1. `invoke_agent` root span (`gen_ai.input.messages`, token usage, session/conversation correlation, `gen_ai.baggage.context`)
  2. `chat` child span (`gen_ai.output.messages`, finish reasons, temperature, max tokens)
  3. `execute_tool` child span (`gen_ai.tool.name`, `gen_ai.tool.call.arguments`, `gen_ai.tool.call.result`)
  4. `mcp` child span (`mcp.method.name` $\in \{\text{tools/call}, \text{resources/read}, \text{prompts/get}\}$, `mcp.server.name`, `mcp.session.id`, `rpc.jsonrpc.*`)
- **Wire Payload Sizes (`1 KiB` synthetic payload baseline)**:
  - `otel_spans`: **`2,940 B/row`** (`ProtoRows` serialized wire bytes)
  - `otel_logs`: **`2,257 B/row`** (structured `pcommon.Map` body + GenAI event attributes)
  - `otel_metrics`: **`1,195 B/row`** (`gen_ai.client.token.usage` delta histograms with trace-correlated exemplars)
- **Synchronous Measurement & Bounded Per-Batch Drain**:
  - `sending_queue` is disabled inside the testbench runner so `ConsumeTraces`, `ConsumeLogs`, and `ConsumeMetrics` measure full end-to-end synchronous execution through `AppendResult.GetResult()` acknowledgement.
  - Each batch derives its own bounded context (`context.WithTimeout(ctx, expCfg.TimeoutSettings.Timeout)`) from a non-cancelling drain context while workers exit once the benchmark duration timer fires.
- **Units & Memory Metrics**:
  - **Binary Byte Units (`MiB`)**: All throughput and memory figures reported by `cmd/bq-otel-testbench` divide byte counts by $1024^2 = 1{,}048{,}576$ (`MiB` and `MiB/s`).
  - **Latency Percentiles & Sample Count (`Samples`)**: Latency percentiles (`p50`, `p95`, `p99`) are computed over completed **batches** (`Samples` = `batches_succeeded`), where each batch contains `batch_size` rows (`500` rows in Suites A/B/D, `250` rows in Suite C). Using the nearest-rank index $\lfloor (N-1) \cdot q \rfloor$, runs with $N < 100$ batches map `p99` to the maximum or second-highest batch sample; `Samples` is therefore reported explicitly in every table.
  - **`Heap Alloc Snapshot (MiB)` vs. `Process Peak RSS (MiB)`**: `Heap Alloc Snapshot (MiB)` reads `runtime.MemStats.HeapAlloc` immediately after the worker pool drains (prior to forcing a post-run `runtime.GC()`), reflecting live plus not-yet-swept Go heap objects. `Process Peak RSS (MiB)` reads `syscall.Getrusage(RUSAGE_SELF).Maxrss`, which is an OS kernel **process-lifetime high-water mark** that increases monotonically across sequential steps in a multi-pool sweep.

## 5. Suite C — AIMD Adaptive Backpressure, Local Offload & Live Native GCS `ObjectRef` Offload (`16 KiB` Payloads)

Suite C profiles three configurations with `16 KiB` (`16,384 B`) prompt/tool payloads and `offload.min_bytes: 4096`:
1. **`bqfake` Local Offload + AIMD Backpressure (`--offload-dir`, `redaction=false`)**: Measures SHA-256 content-addressed local disk offload and AIMD adaptive batch splitting under injected `FaultDelayedAck` (`15 ms` ack delay every 3rd batch, `latency_threshold: 7.5ms`) and `FaultResourceExhausted` (`RESOURCE_EXHAUSTED` every 10th batch).
2. **`bqfake` Step-0 Redaction $\rightarrow$ Local Offload + AIMD Backpressure (`--offload-dir`, `redaction=true`)**: Verifies that Step-0 redaction runs **before** offload so offloaded blobs on disk contain `[REDACTED]` placeholders rather than raw credentials, and measures the RE2 regex scan cost across `16 KiB` payloads.
3. **Live BigQuery + Native GCS Offload (`--mode=live -offload-gcs-bucket=<gcs-bucket>`, `redaction=true`)**: Exercises the exporter's full production pipeline (`Redactor -> GCSBlobStore -> payload_refs (ObjectRef) -> ProtoRows -> BigQuery Storage Write API`), populating both the `<offloaded:gs://...>` inline placeholder and the structured `payload_refs` (`ObjectRef`) column in BigQuery.

### Key Findings from Live BigQuery Measurements

1. **Stream Pool Sweet Spot (`write.stream_pool_size: 4`)**:
   - On live BigQuery newly auto-created tables, increasing `write.stream_pool_size` from `1` to `4` increases `otel_spans` throughput by **`+58.3%`** (from `15,206.1` spans/s / `42.64 MiB/s` to **`24,065.7` spans/s / `67.48 MiB/s`**), `otel_logs` throughput by **`+43.9%`** (from `18,485.8` logs/s to **`26,603.7` logs/s / `57.26 MiB/s`**), and `otel_metrics` throughput by **`+73.9%`** (`25,647.5` pts/s at `pool=4`, peaking at **`26,501.5` pts/s** at `pool=2`), while cutting `p95` batch latency from `~1.0 s` to **`543–579 ms`**.
   - On freshly created tables (first ~15 seconds after `CREATE TABLE`), opening `8` or `16` simultaneous `_default` streams triggers initial BigQuery Storage Write stream creation and tablet split warm-up tail spikes (`p95 ~ 0.84–1.29 s` across a 2-second burst window), whereas `write.stream_pool_size: 4` (with `connection_pool_size: 4`) saturates `57–67 MiB/s` cleanly.
2. **Exporter Resource Efficiency**:
   - Across all 15 live BigQuery runs (`stream_pool_size` `1..16`), the exporter consumes **`1.23–1.65` vCPU cores per `10,000` rows/sec**, **`17.7–54.4 MiB` of Go heap (`HeapAlloc` snapshot)**, and a steady **`137.5 MiB` Process Peak RSS**.
3. **Production Sizing Rule of Thumb**:
   - **Up to `15,000` spans/s (`~42 MiB/s` wire)**: `write.stream_pool_size: 1` (default) with `enable_multiplexing: true`, `2` vCPU, `512 MiB` container memory limit.
   - **`15,000` to `25,000` spans/s (`42–68 MiB/s` wire)**: `write.stream_pool_size: 4`, `write.connection_pool_size: 4`, `write.backpressure.enabled: true`, `4` vCPU, `1 GiB` container memory limit.
   - **Above `25,000` spans/s (`>68 MiB/s` wire)**: Scale horizontally across `2+` Collector replicas with `write.stream_pool_size: 4` per replica (or `stream_pool_size: 8` once destination table partitions are warm).
